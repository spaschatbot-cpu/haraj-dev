# خريطة الطريق — حراج واحد v2

نظام جديد كامل، بقاعدة بيانات جديدة، يحلّ محلّ `applicationtest` القديم.

| البند | القرار |
|---|---|
| الخلفية | Django 5.2 LTS · DRF · PostgreSQL 17 · Celery + Redis |
| التطبيق | Flutter (أصلي) على الـAPI |
| لوحة الإدارة | ويب داخل نفس مشروع Django |
| الاستراتيجية | بناء مستقل + ترحيل بيانات + تحويل مرة واحدة بعد فترة تشغيل متوازٍ للقراءة |
| نقطة البداية | محرّك الفلوس |

اقرأ [الدستور](../.specify/memory/constitution.md) قبل أي شيء. كل فيز هنا له
مجلد في `specs/` فيه `spec.md` (المطلوب ولماذا) و`tasks.md` (تاسكات قابلة
للتنفيذ)، ويُضاف `plan.md` (التصميم التقني) عند بدء الفيز.

### التتابع الواقعي

```
001 ──► 002 ──► 003 ──► 004 ──────────────────┐
   │                                           ├──► 010
   └──► 005 ──► 006 ──► 007 ──┬──► 008         │
                   │           └──► 011        │
                   └──► 009 ───────────────────┘
```

001 يفتح كل شيء. بعده مساران متوازيان: **مسار المال** (002 → 003 → 004) و**مسار
المزاد** (005 → 006). يلتقيان عند 007، ومنه تتفرّع **قناتا العميل**: التطبيق
(008) والويب (011)، وكلتاهما تستهلك مخطط OpenAPI نفسه ولا تملك نقطة خاصة بها.
الفيز 009 يبدأ بمجرد استقرار 002 و005.

القناتان لا تُبنيان معاً — الفريق ثلاثة. أيّهما أولاً هو **Q6** أدناه.

## معيار "منتهي" لأي فيز

الفيز لا يُغلق إلا باكتمال الخمسة:

1. كل تاسكاته مؤشَّرة منتهية في `tasks.md`.
2. اختبارات الفيز خضراء على PostgreSQL بإعدادات الإنتاج.
3. `verify_ledger()` نظيف (لأي فيز يمسّ المال).
4. لا بند في الدستور مكسور — تُراجَع القائمة بنداً بنداً.
5. `spec.md` محدَّث بما تغيّر أثناء التنفيذ، لا كما كان مكتوباً في البداية.

## ما هو موجود بالفعل في المستودع

قبل كتابة هذه الخطة كُتب **نموذج أولي** للفيز 002 (الدفتر وطبقة الخدمة
والاختبارات) وهو في `backend/`. هو مرجع للشكل المقصود، **وليس** كوداً معتمَداً:
لم يُشغَّل ولا مرة لأن PostgreSQL لم يكن مثبَّتاً. تاسكات الفيز 001 و002 تتعامل
معه على أنه مسودّة تُراجَع وتُثبَّت، لا على أنه منتهٍ.
