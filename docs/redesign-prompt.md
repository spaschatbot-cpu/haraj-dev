# برومبت إعادة تصميم صفحة — حراج واحد v2

> يُنسخ كاملاً ويُعطى لأيّ نموذج AI مع كود الصفحة المطلوبة. الأقسام ١–٦ ثابتة عن
> المشروع، والقسم ٧ يُملأ لكلّ صفحة.

---

أنت مصمّم واجهات ومطوّر واجهة أمامية متمرّس. مطلوب منك **إعادة تصميم صفحة** في مشروع «حراج واحد» مع تحسين واجهة المستخدم وتجربة المستخدم لتبدو أكثر عصرية، **مع الحفاظ الكامل على المنطق والبيانات والوظائف كما هي**. اقرأ القواعد كلها قبل أن تلمس سطراً.

## ١ — ما المشروع

«حراج واحد» منصّة سعودية لمزادات السيارات (سيارات التأمين والحوادث والتشليح). النسخة الحالية (v2) تعيد بناء نظام قديم (v1، PHP) كان يعاني من أعطال مالية: تأمين خُصم مرتين، مدين يزايد بلا رصيد، استردادات مكرّرة. لذلك قلب v2 **دفتر مالي بقيد مزدوج** وكل الواجهات تقف فوقه وتعرض ما يقوله ولا تحسب شيئاً بنفسها.

### دورة العميل كاملة

1. **الدخول** برقم الجوال ورمز SMS (بلا كلمة مرور). الحساب الجديد أو الناقص يُكمل بياناته بعد الرمز: فرد (الاسم، رقم الهوية، المدينة) أو شركة (المفوّض، الهوية، اسم المنشأة، السجل التجاري، الرقم الضريبي، العنوان الوطني كاملاً).
2. **التأمين**: يودع العميل وديعة ثابتة **١٠٬٠٠٠ ريال** في محفظته (بالبطاقة عبر بوابة دفع، أو حوالة يقيّدها الموظف). تأمين واحد يكفي لمزاد كامل مهما زايد على سيارات.
3. **المزاد** أسبوعي، فيه ٢٠٠–٤٠٠ سيارة، كلٌّ لها لوت ورقم لوحة وشاصي وصور. المزايدة مغلقة (لا يرى المزايد أرقام غيره)، والمزايدة تحجز التأمين. خفض المزايدة مسموح بتأكيد صريح.
4. **اتخاذ القرار** بعد نهاية المزاد: الموظف يرى أعلى عرض على كل سيارة ويقبل أو يرفض. القبول = ترسية، وتصدر **فاتورة** = السعر + رسوم إدارية **٨٠٠ ريال** + ضريبة **١٥٪** على المجموع.
5. **السداد** بحوالة بنكية فقط، يقيّدها الموظف من اللوحة (التأمين لا يُحتسب من ثمن السيارة، والبطاقة لا تُسدَّد بها سيارة).
6. **الخروج**: بعد السداد يصدر أمر خروج بباركود وإقرار استلام يُطبع.
7. **الاسترداد**: بعد السداد يعود التأمين «متاحاً» ويطلب العميل استرداده (بشرط رفع صورة الآيبان)، وتنفّذه المحاسبة عبر أودو.

### فلوس العميل في «دلاء» — تُعرض كما هي

| الدلو | معناه للعميل |
|---|---|
| `insurance_free` | تأمين متاح — يزايد به ويسترده |
| `insurance_held` | محجوز لمزاد جارٍ |
| `insurance_locked` | مقفول على فاتورة غير مسدَّدة |
| `wallet` | محفظة عامة (نادر الاستخدام) |

### الحالات كما تصل من الخادم (بنصّها العربي)

- **المزاد**: مسودة · مجدول · جارٍ · منتهٍ · مُسوّى · ملغى
- **السيارة**: مسودة · معروضة · تحت المزايدة · بانتظار قرار المالك · مرسّاة · مرفوضة · مفوترة
- **الفاتورة**: مسودة · مستحقة · مسدَّدة جزئياً · مسدَّدة · ملغاة
- **طلب الاسترداد**: مُقدَّم · أُرسل للمحاسبة · نُفِّذ · مرفوض · ألغاه العميل

## ٢ — الواجهات الثلاث

| الواجهة | لمن | التقنية | ملاحظات |
|---|---|---|---|
| **لوحة الإدارة** | الموظفون | Django templates + CSS مخصص (`backend/apps/console/static/console/app.css`) + قليل من JavaScript عادي بلا إطار | شريط جانبي ٣٩ صفحة، جداول عريضة (حتى ١٤ عموداً)، نوافذ `<dialog>` للأفعال، وضع داكن، اختيار أعمدة الجدول محفوظ للمستخدم |
| **موقع العملاء** | العميل | Next.js 16 App Router + Tailwind v4 + React Server Components، كل النماذج Server Actions | يعمل بلا JavaScript على العميل، رسائل الخادم تُعرض عبر flash cookie لمرة واحدة |
| **تطبيق الجوال** | العميل | Flutter + Riverpod + go_router، عميل API مولَّد من OpenAPI | طبقات domain/data/presentation، الترجمة من `app_ar.arb` (العربية هي القالب) |

**قاعدة تحكم الثلاثة:** الأهلية والتسعير والحدود وحالات الاكتمال تُسأل مرة واحدة في الخادم ويُعرض جوابها. لا واجهة تحمل قاعدة عمل.

## ٣ — قواعد ثابتة لا تُكسر

1. **عربية وRTL في كل شيء.** الخط في الويب IBM Plex Sans Arabic. الأرقام والمبالغ بأرقام لاتينية (0-9) وبصنف `money`/`tnum` (متساوية العرض، لا التفاف). الأرقام التعريفية (رقم المزاد 1019، اللوت 12، السنة 2019) **بلا فاصلة آلاف**؛ المبالغ والكميات بفاصلة (43,470.00).
2. **الواجهة لا تحسب ولا تقرّر.** كل مبلغ ومجموع وضريبة ومتبقٍّ وحالة وأهلية يأتي حقلاً من الخادم ويُعرض كما هو. ممنوع `amount - paid` أو `price * 1.15` أو «لو الاسم فاضي فالملف ناقص» في الواجهة.
3. **لا تغيير في البيانات ولا النماذج**: نفس الحقول، نفس `name`، نفس المسارات والـactions، نفس رسائل الخادم. إعادة التصميم شكل وترتيب وتجربة فقط.
4. **بلا JavaScript جديد** في موقع العملاء (النماذج تعمل بلا JS). في اللوحة JavaScript عادي بلا مكتبات، وفي ملف ثابت لا داخل القالب.
5. **الجمهور سعودي غير تقني.** نصوص قصيرة، أزرار **بالكلمة** («قبول»، «رفض»، «سدّد»، «أودِع») لا أيقونات وحدها. الفعل الذي لا رجعة فيه (ترسية، رفض، إنهاء مزاد، مصادرة) يأخذ تأكيداً **يسمّي اللوت والمبلغ** في نافذة من التصميم نفسه، لا `confirm()` المتصفح.
6. **الرموز SVG مضمّنة**، لا محارف يونيكود مثل ✕ أو ← (تُرسم مختلفة بين الأجهزة).
7. **الألوان من متغيرات CSS** لا قيم صريحة، و**الوضع الداكن** مدعوم في اللوحة والتطبيق.
8. **متجاوب**: صفحات العملاء للجوال أولاً. جداول اللوحة العريضة تحتاج حلاً على الشاشات الضيقة **بلا إخفاء بيانات مهمة** (اللوحة فيها اختيار أعمدة، لا تكسره).
9. **لا صفحات أو روابط أو حقول مخترعة.** رابط إلى صفحة غير موجودة = عطل. لو تحتاج بياناً غير موجود في الكود، اذكره في قائمة «يحتاج الخادم».
10. **التعليقات العربية في الكود تبقى.** تشرح قرارات سابقة وأسبابها (كثير منها أعطال حقيقية من v1)، ولا تُحذف ولا تُختصر.
11. **الحالات الفارغة والأخطاء** تُصمَّم: «لا مزايدات على هذه السيارة» ببطاقة واضحة لا سطر عارٍ، وخطأ الحقل تحت خانته لا في أعلى الصفحة.

## ٥ — ما يعنيه «عصري» هنا

- تسلسل بصري واضح: الرقم أو الفعل الأهم أكبر وأوّل. في صفحة الفاتورة «المتبقّي» أبرز من «صدرت في».
- بطاقات ذات معنى لا صناديق للزينة: كل بطاقة تجيب سؤالاً واحداً.
- مساحات مريحة، محاذاة ثابتة، وأعمدة أرقام محاذاة على الفاصلة العشرية.
- زر رئيسي واحد بارز في كل شاشة، والباقي ثانوي.
- الحالة تُقرأ من اللون **والكلمة** معاً (مستحقة/مسدَّدة/ملغاة)، لا من اللون وحده.
- الجوال: عناصر تُلمس بإصبع (44px)، ولا تمرير أفقي في صفحات العملاء.

## ٦ — المطلوب منك

1. اقرأ الصفحة الحالية وافهم كل عنصر ووظيفته قبل أن تعدّل.
2. أعد التصميم وفق القواعد أعلاه.
3. سلّم:
   - **(أ)** قرارات التصميم في ٥–١٠ أسطر: ماذا غيّرت ولماذا.
   - **(ب)** الكود الكامل للصفحة بعد التعديل، بنفس التقنية ونفس الملفات، جاهزاً للاستبدال.
   - **(ج)** قائمة «يحتاج الخادم»: أي تحسين لم تستطع عمله لأنه يحتاج بياناً أو نقطة API غير موجودة — لا تخترعه.
4. لا تغيّر ملفات غير الصفحة وملف CSS/المكوّنات التي تخصّها.
