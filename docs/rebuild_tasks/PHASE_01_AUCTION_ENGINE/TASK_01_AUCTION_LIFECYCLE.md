# TASK 01: محرك دورة حياة المزاد (Auction Lifecycle Engine)

## ١. الهدف ونطاق المهمة
بناء محرك دورة حياة المزاد الزمني المؤتمت (Deterministic Time-Driven Lifecycle Engine). المحرك مسؤول عن تحويل حالات المزاد عبر خط زمني صارم، وفصل التحويل الزمني عن زيارات الويب، وضمان مزامنة حالة سيارات المزاد تلقائياً.

---

## ٢. الأهمية ومعدل الاستخدام
- **الأهمية:** 🔴 حرجة جداً (Core Engine) — أي خطأ يؤدي إلى فتح مزاد قبل وقته أو عدم إغلاقه في وقته المحدد.
- **معدل التنفيذ:** يعمل كمهمة خلفية كل 60 ثانية (Cron/Worker)، ومع كل قراءة لقائمة المزادات كشبكة أمان.

---

## ٣. الحالات والانتقالات الزمنية (State Machine)

```
[ later / upcoming ]
        │
        ▼ (بلوغ start_time)
     [ soon ]  ── (المعاينة فقط - لا مزايدة)
        │
        ▼ (بلوغ start_time الفعلي للمزايدة)
    [ active ] ── (المزايدة مفتوحة - الودائع تُحجز)
        │
        ▼ (بلوغ end_time)
    [ ended ]  ── (انتهاء الوقت - إيقاف المزايدة - تشغيل تسوية التأمين)
        │
        ▼ (اتخاذ القرار، إصدار الفواتير، وظهور مزاد منتهٍ أحدث)
  [ not_active ] (أرشفة المزاد - غير مرئي للجمهور)
```

### قواعد التحويل الإلزامية:
1. **الانتقال تتابعي:** `soon` -> `active` -> `ended` -> `not_active`. يمنع القفز المباشر.
2. **قاعدة المزاد المنتهي الوحيد:** يظهر للعملاء في واجهة التطبيق **مزاد منتهٍ واحد فقط** (الأحدث) لعرض النتائج وقرارات الترسية. بمجرد دخول مزاد جديد حالة `ended`، يتحول المزاد الأقدم تلقائياً إلى `not_active`.
3. **تزامن حالة السيارات:** حالة المركبة تتبع حالة مزادها. بمجرد انتقال المزاد إلى `active` تصبح سياراته `active`، وعندما ينتهي تصبح `ended`.
4. **تزامن تسوية التأمين:** لحظة تحول المزاد إلى `ended`، يُطلق المحرك إشارة تسوية التأمين فوراً لحجز ودائع المنافسين ومنع استردادها.

---

## ٤. الجداول والأعمدة في قاعدة البيانات

### جدول المزادات `auctions`:
- `id` (int, PK, Auto Increment)
- `name_of_auction` (varchar 255) — اسم المزاد (مثال: مزاد الرياض الأسبوعي 1015)
- `start_time` (datetime, NOT NULL) — وقت بدء المزاد (يخزن UTC)
- `end_time` (datetime, NOT NULL) — وقت انتهاء المزاد (يخزن UTC)
- `status` (enum: 'soon', 'active', 'ended', 'not_active') — مفهرس (INDEX)
- `type_auctions` (varchar 50, DEFAULT 'sealed') — نوع المزاد (مغلق دائماً Sealed-bid)
- `increment` (decimal 12,2, DEFAULT 500.00) — الحد الأدنى لزيادة المزايدة
- `fees` (decimal 12,2, DEFAULT 0.00) — الرسوم الإدارية الثابتة للمزاد
- `vat_type` (varchar 50, DEFAULT 'standard') — نوع الضريبة (15%)
- `insurance_amount` (decimal 10,2, DEFAULT 10000.00) — مبلغ التأمين المطلوب لدخول المزاد
- `is_mega_auction` (tinyint 1, DEFAULT 1) — علم المزاد المجمع متعدد السيارات

### جدول سيارات المزاد `auction_vehicles`:
- `id` (int unsigned, PK)
- `auction_id` (int, FK -> auctions.id, INDEX)
- `lot_number` (varchar 100) — رقم اللوت التتابعي في المزاد
- `vehicle_name` (varchar 255)
- `starting_price` (decimal 12,2, NOT NULL) — سعر الافتتاح (لا تقبل مزايدة أقل منه)
- `status` (varchar 20, INDEX) — `active`, `ended`, `sold`, `unsold`, `withdrawn`
- `winner_user_id` (int, NULL) — معرّف الفائز بعد اعتماد المالك
- `final_price` (decimal 12,2, NULL) — سعر الترسية النهائي

## ٥. الفخاخ التقنية السابقة (Gotchas to Avoid)
1. **فخ التحويل عند أول طلب زائر (Request-Driven Lifecycle):**
   - في النظام القديم: المزاد لا يفتح إذا لم يقم زائر بفتح الصفحة الرئيسية.
   - **الحل:** مجدول مهام حقيقي (Cron Job / Worker) ينبض كل دقيقة بشكل مستقل تماماً عن طلبات الويب.
2. **فخ التوقيت UTC مقابل توقيت السعودية (UTC+3):**
   - في النظام القديم: `NOW()` يرجع توقيت السيرفر بينما واجهات الإدخال تأخذ توقيت الرياض مما سبب فارق 3 ساعات.
   - **الحل:** توحيد جميع الأعمدة والعمليات الحسابية الداخلية على `UTC` الصارم، والتحويل إلى `Asia/Riyadh` يحدث حصرياً في طبقة العرض (UI Presentation Layer).

---

## ٦. معايير القبول والاختبار (Acceptance Criteria)
- [ ] عند حلول `start_time` ينتقل المزاد تلقائياً إلى `active` دون أي تدخل بشري.
- [ ] عند حلول `end_time` ينتقل المزاد وتغلق بوابة المزايدة في نفس الثانية (تمنع أي مزايدة جديدة برمز `AUCTION_NOT_LIVE`).
- [ ] المزاد المنتهي الأقدم يتحول تلقائياً إلى `not_active` بمجرد انتهاء مزاد أحدث منه.
- [ ] وجود قفل تنفيذي (Mutex / Atomic Lock) لمنع التنازع في حال تشغيل عمليتين متوازيتين للجدولة.
