# TASK 03: منطق خفض السعر وتأكيده الصريح (Bid Downgrade & Explicit Confirmation)

## ١. الهدف ونطاق المهمة
تطبيق سياسة المنصة الخاصة بالسماح للعميل بخفض قيمة مزايدته في المزاد المغلق (Sealed-bid)، مع وضع حماية برمجية تمنع الخفض غير المقصود أو الناتج عن إعادة إرسال المتصفح لبيانات سابقة.

---

## ٢. الأهمية ومعدل الاستخدام
- **الأهمية:** 🔴 حرجة جداً (Financial Safety) — تسببت سابقاً في خسارة مالية مثبتة لعميل تجاوزت 9,000 ريال بسبب خطأ في المتصفح.
- **معدل الاستخدام:** متكرر أثناء ساعات المزاد عند إعادة تقييم المزايدين لسياراتهم.

---

## ٣. فلسفة العمل (Business Rationale)
- في المزادات التقليدية المفتوحة، لا يُسمح بتراجع السعر لأن المتنافسين يرون المزايدات علناً.
- **في حراج واحد، المزاد مغلق تماماً (Sealed-bid):** لا أحد يرى عروض الآخرين، والبيع خاضع لموافقة المالك لاحقاً. لذا قررت الإدارة السماح للعميل بتعديل سعره بالزيادة أو النقصان حتى موعد الإغلاق.
- **الخطر:** إذا فتح العميل تبويبين، أو أعاد المتصفح إرسال Form قديم بسعر أقل، يُستبدل عرضه الأعلى بعرض منخفض دون أن يدري، مما يحرمه من الفوز.

---

## ٤. الخوارزمية وتدفق التأكيد (Downgrade Flow)

```
طلب المزايدة: NewAmount
السعر الحالي المسجل في قاعدة البيانات للسيارة: CurrentAmount
   │
   ├─► NewAmount > CurrentAmount
   │      │
   │      └─► تنفيذ فوري: زيادة طبيعية دون الحاجة لتأكيد.
   │
   ├─► NewAmount == CurrentAmount
   │      │
   │      └─► لا تغيير (No-op)، الرد بنجاح مع الإبقاء على السعر.
   │
   └─► NewAmount < CurrentAmount  (خفض السعر)
          │
          ├── هل أرسل العميل العَلَم: confirm_lower = true ؟
          │      │
          │      ├─► نعم:
          │      │     ١. تسجيل الحركة في سجل التدقيق المالي مع توثيق الخفض.
          │      │     ٢. تحديث السعر إلى NewAmount.
          │      │     ٣. إرجاع 200 OK.
          │      │
          │      └─► لا:
          │            ١. رفض الطلب فوراً برمز HTTP 409 Conflict.
          │            ٢. إرجاع كود الخطأ: LOWER_NEEDS_CONFIRM.
          │            ٣. إرجاع القيمة الحالية المسجلة في السيرفر والقيمة الجديدة المطلوبة:
          │               {
          │                 "ok": false,
          │                 "error": "LOWER_NEEDS_CONFIRM",
          │                 "current_amount": 45000,
          │                 "requested_amount": 40000,
          │                 "message": "سعرك الحالي أعلى من السعر الجديد. هل تؤكد خفض عرضك؟"
          │               }
```

---

## ٥. سلوك الواجهة الأمامية (Frontend Handling)
1. عند استلام الخطأ `409 LOWER_NEEDS_CONFIRM`، تفتح الواجهة نافذة حوارية بارزة (Modal) تحذر العميل:
   - "سعرك الحالي المسجل هو: **45,000 ر.س**"
   - "أنت تحاول خفض السعر إلى: **40,000 ر.س**"
   - "تنبيه: خفض السعر قد يقلل فرصك في قبول العرض من قبل المالك."
2. عند ضغط "تأكيد الخفض"، يعيد التطبيق إرسال نفس الطلب مع إضافة الحقل: `confirm_lower: true`.

---

## ٦. القواعد الأمنية الصارمة
1. **لا تثق أبداً بالقيمة القادمة من العميل:** المقارنة تتم دائماً بين `NewAmount` والقيمة الحقيقية المخزنة في قاعدة البيانات للسيرفر لحظة التنفيذ، وليس بأي قيمة مخبأة في كاش المتصفح.
2. **قفل الصف تشاؤمياً (`SELECT amount FROM bids ... FOR UPDATE`):** لضمان عدم وجود طلبين متزامنين لرفع وخفض السعر في نفس الجزء من الثانية.

---

## ٧. معايير القبول والاختبار
- [ ] أي طلب يتضمن سعراً أقل من السعر المسجل يُرفض بـ `409` طالما لم يرسل `confirm_lower=true`.
- [ ] إرسال `confirm_lower=true` يؤدي إلى اعتماد السعر الجديد بنجاح وتسجيل الحالة كـ `downgrade`.
- [ ] عدم استجابة النظام لأي محاولة تلاعب بالواجهة لتخطي التأكيد.
